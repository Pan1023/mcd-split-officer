# 麦麦拆单官 · mcd-split-officer

> 一桌人一起点麦当劳，谁都不想当那个"算不明白"的人。
> 这个 Skill 把一桌人的订单**拆成几张单**，让每一张都刚好用上最划算的券，再算出**每个人该付多少**。

## 30 秒跑起来

不需要 Token，不需要联网，不需要 `npm install`：

```bash
git clone https://github.com/Pan1023/mcd-split-officer.git && cd mcd-split-officer
node bin/selftest.js    # 先自检：7 个手算用例 + 一致性检查
node bin/demo.js        # 场景一：4 人拼单，看能省多少
node bin/demo.js --gap  # 场景二：差一点到门槛，看加购建议
```

跑完会得到一份拆单方案，和一张可以直接截图发群的战绩表 `out/split-card.html`。

> 演示用的是 `fixtures/` 里录好的 MCP 响应，所以断网也能跑通全链路。

**场景二会给你这种建议**（不只算，还劝你别急着下单）：

```
【还能再省？】
  · 再加 ¥4.50 就够「满60减15」：补 1 份「苹果派」（¥8.00），
    总价反而少 ¥7.00，变成 ¥48.50
```

## 它到底在算什么

一桌 4 个人点了 10 件商品，一共 ¥146.50。你有三种玩法：

| 玩法 | 实付 | 说明 |
|---|---|---|
| 一次点完，用「满60减15」 | ¥131.50 | 最省事的做法 |
| 拆成 3 单，用「1+1随心配」+「满60减15」 | ¥106.70 | **本工具给出的方案** |

差的这 ¥24.80 不是运气，是**穷举出来的**。

问题的难点在于：

- 一张订单**只能用一张券**，所以「1+1 组合价」和「满减」互斥
- 满减有门槛（满 40 / 满 60），凑不够就白搭，多凑又浪费
- 组合价要挑"哪两件去凑最划算"—— 拿最贵的两件去凑，省得最多
- 组合价能用几次，取决于你有几件**符合范围**的商品

所以本质是：**把 N 件商品划分成若干堆，每堆配一张最优券，使总和最小。**
这是个集合划分问题，商品一多就爆炸。本项目用「子集预处理 + 划分 DP」求**精确最优解**，
12 件以内毫秒级，不靠启发式猜。

## 示例输出

> 结构示意。具体怎么分组由算法决定（优惠相同的分法可能有多种，都是最优解）。

```
原价合计   ¥146.50
拆单后     ¥106.70    省 ¥39.80（27.2%）
解法       精确最优（子集枚举 + 划分 DP）

【拆单方案】共 4 单
 单 1  1+1随心配 13.9
   麦乐鸡（5块）  ¥13.50   [老陈]
   中薯条        ¥12.50   [小周]
   小计 ¥13.90（省 ¥12.10）
 单 2 ~ 单 3  同上，两两组合
 单 4  满60减15
   巨无霸 / 麦辣鸡腿堡 / 板烧鸡腿堡 / 双层吉士汉堡
   小计 ¥65.00（省 ¥15.00）

【每人应付】优惠按各自商品金额占比分摊
```

最后那个「每人应付」是本项目比较在意的细节：
优惠**不是简单 AA**，而是按每个人点的金额占比分摊。点得贵的人摊得多，这才叫公平。

## 接入真实 MCP

真实链路是：**MCP 取数 → 归一化 → 脚本算钱 → 模型说人话**。

```
麦当劳 MCP (mcd-mcp)
        │  菜单 / 券 / 价格
        ▼
src/normalize.js      ← 只在这一层适配字段名
        │  统一结构
        ▼
src/optimizer.js      ← 纯函数，只认数字
        │
        ▼
src/report.js         ← 文本报告 / 战绩表 HTML
```

在 WorkBuddy 里配置连接器（Token 从 `open.mcd.cn` 控制台激活后复制）：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer 你的Token" }
    }
  }
}
```

细节和工具名对应关系统一写在 [MCP_INTEGRATION.md](MCP_INTEGRATION.md)。

**Token 绝不写进仓库**，`.env` 已在 `.gitignore` 里。

## 设计取舍

**为什么不让大模型直接算钱？**
因为模型心算价格会错，而且错得很自信。这里的每个数字都由代码产出，
模型只做三件事：听懂需求、组织语言、把结果讲成人话。

**为什么要精确解而不是贪心？**
贪心在"券互斥 + 门槛"这种约束下很容易陷在局部最优。
反正件数不多，直接枚举所有分法、用 DP 合并，答案就是最优的——
这样回答"凭什么这么分"时，才有底气。

**为什么金额全用「分」做整数？**
`21.9 * 3` 在浮点数里不等于 `65.7`。涉及钱就别用浮点。

## 已知限制

- 超过 12 件商品会降级为贪心近似，输出里会明确标注
- 券能否核销取决于门店、时段、会员身份，本工具不保证
- 示例菜单里是近似价格，**真实价格必须以 MCP 返回为准**
- 不处理配送费、包装费
